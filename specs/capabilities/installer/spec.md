# Capability — Installer and `rigorkit` command

> Status: current · Owner repo: rigorkit · DoD: critical (writes shell startup files, global rules and user folders)

## Context and goal
rigorkit installs with one line into `~/.rigorkit`, exposes a `rigorkit` command with help and a manual page, installs packs through `rigorkit install` (same options as `install.sh`), runs helper scripts from the clone and lets users add their own packs and scripts in a custom area that takes precedence over official ones. Once a day it checks for a newer release, tells the user in the terminal and through agents, and `rigorkit update` moves the clone and refreshes the global scope with the user's consent.

## Definitions
- **Clone**: `~/.rigorkit`; a **rigorkit clone** is a git work tree with `VERSION` and `install.sh` at its root (forks count); a **development clone** is any other one.
- **Custom area**: `~/.rigorkit/custom/{packs,scripts}`, git-ignored, the same for every clone; rigorkit never modifies it.
- **Startup block**: lines between `# rigorkit:start` and `# rigorkit:end` in `.zshrc` (`$ZDOTDIR/.zshrc` when set), `.bashrc` and an existing `.bash_profile` that does not load `.bashrc`; idempotent; appends the clone's `bin/` to the end of `PATH` and its `man/` to `MANPATH` without hiding system pages, and sources `lib/startup.sh` when the clone has it (the update check).
- **Newest release tag**: the `vX.Y.Z` tag with the highest semantic version.
- **State**: `~/.local/state/rigorkit/` (mode 700): `check` (last check time, newest version, declined check), `notice` (one line for agents), `global` (global record), locks.
- **Global record**: what `rigorkit install --global` of the clone wrote: pack/agent pairs, recorded version, per skill/agent copy and rules block its path and a SHA-256 fingerprint of the normalized content (LF/CRLF and trailing blanks ignored), plus the declined content of a kept copy.
- **User configuration**: `~/.config/rigorkit/config`, `update_mode` (`prompt` default, `reminder`, `disabled`) and `update_days` (whole days ≥ 1, default 1).
- **Rules placeholder**: `{{RIGORKIT}}` in a pack's `rules.md`, rendered as the single-quoted absolute path of the installing clone's `bin/rigorkit`.

## Current contracts
- RF-1: `tools/install-remote.sh` (one line: `sh -c "$(curl -fsSL …/main/tools/install-remote.sh)"`) clones the newest release tag (or `RIGORKIT_REF`) from `https://github.com/harrypotter48/rigorkit.git` (or `RIGORKIT_REMOTE`: https, `user@host:path`/`ssh://`, or a local path only; values or parts starting with `-` refused) into a temporary folder, refuses a ref without `bin/rigorkit`, removes group/other write bits, moves it into `~/.rigorkit` (also when it holds only `custom/`), creates missing custom folders never group/other-writable, adds startup blocks with `<file>.rigorkit.bak` backups (original mode) and installs no pack. Nothing from the clone runs before the tag is checked out; failures leave no new clone and no temporary folder.
- RF-2: An existing clone gets only missing startup blocks; `RIGORKIT_REF`/`RIGORKIT_REMOTE` are then ignored with a warning; a folder that is not a clone is refused.
- RF-3: `rigorkit install` and `install.sh` behave identically and as `install.sh` 0.1.0 except: no script copy, rendered rules (refused if the clone path holds `'` or a newline), `<file>.rigorkit.bak` with the original mode, custom packs in `--list`/`all`/uninstall, `--help` in any position, the global record (written only by the clone at `~/.rigorkit`; skipped differing copies keep their earlier data; `--uninstall-rules` removes its rules lines; an unreadable record is renamed `global.corrupt`; `--dry-run` and project installs never touch it), and for `rigorkit install` only the check and notice of interactive runs.
- RF-4: A custom pack replaces the whole official pack with the same name; custom packs named `all` or with `,`/whitespace are ignored with a warning; shadowed packs and `custom/scripts` shadowing official scripts are reported.
- RF-5: `rigorkit script <name> [args]` runs the first match in `custom/scripts`, custom packs, then official packs not replaced (byte order), with unchanged args and its exit status (interactive runs may print the update notice on standard error first); names missing, starting with `-`, or with `/`/`..` are refused (2); not found 127; not executable 126.
- RF-7: Releases: a merge to `main` whose `VERSION` is an unreleased `X.Y.Z` greater than every `vX.Y.Z` tag publishes the annotated tag `v<VERSION>` (`.github/workflows/release-tag.yml`: read-only `test` job, then a `tag` job without actions that pushes only that tag with the workflow token); a released version changes nothing; published tags cannot be moved or deleted (repository ruleset).
- RF-6: `rigorkit`, `help`, `--help`, `-h` list `install`, `update`, `script`, `help`; `help <cmd>` and `<cmd> --help` show `help/<cmd>.txt`; `man rigorkit` is `man/man1/rigorkit.1`, generated from `help/` by `tools/generate-man.mjs`; its `--check` fails on command/option/man drift (including `lib/update.sh` options), on a `VERSION` without a complete `CHANGELOG.md` section (`Global rules:`, `New packs:`) and on any file in `bin/` other than `rigorkit`.
- RF-8: Update check: at an interactive shell start (no `-c`, terminal input and output) and in interactive `rigorkit` runs other than `update` and `--dry-run`, at most once per `update_days`, `lib/check.sh` runs detached (SIGHUP ignored, no terminal reads or credential prompts, 30 s limit, one at a time) and records the newest valid `vX.Y.Z` of `origin`; a failure keeps the previous result; a successful check clears an earlier no. Development clones never check.
- RF-9: Notices: `prompt` asks at shell start (`y`/`yes` runs `rigorkit update`; anything else is a no until the next successful check); `reminder` prints one line at shell start; both print the line on standard error in interactive runs other than `update`/`help`; `disabled` does nothing and removes the agent notice. Nine entry skills tell the user once per session the line in `~/.local/state/rigorkit/notice`. Only validated versions are ever printed.
- RF-10: `rigorkit update [--dry-run]`: one at a time (lock with owner pid); refuses local changes in the clone (except execute-bit-only changes of official scripts, which it repairs), an unreachable remote, a newest tag whose `VERSION` differs, a tag not descending from the clone, or a release tracking `custom/`; moves to the newest tag and verifies a clean work tree (rolls back otherwise); then the new code's phase 2 (contract: the clone's `lib/update.sh` exec'd by the lock owner with `RK_UPDATE_FROM=<previous>`) prints the changelog of every skipped version and asks, each item only on a yes: outdated startup blocks (per file), unedited global copies (one group), changed rules blocks (per file, with diff), edited copies (overwrite or keep, with diff), packs new in the changelog (per pack), old scripts in `~/.local/share/rigorkit/scripts` (only regular files rigorkit published). Without a terminal every question is a no, listed as skipped; the recorded version advances only when nothing was declined, skipped or failed. `--dry-run` reads the staged release with the running code, asks nothing and writes nothing outside `~/.rigorkit/.git`. Printed text from a release (changelog, diffs, names, versions) has control characters replaced by `?`. A 0.2.0 clone moves once by the README commands.
